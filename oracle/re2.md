# The RE2 oracle

RE2 has no reference source to build a tracer into, so `scripts/oracle-re2.py`
traces the original executable from outside and writes the same
`oracle-trace v1` file (`trace-v1.md`) as the RE1 reference.

It needs a retail install holding `bio2 1.10.exe`, Classic Rebirth's `ddraw.dll`
and `data/`, named by `--game` or `ARKLAY_RE2_ROOT`. On Linux it also needs
`wine`, `Xvfb` and, for screenshots, ImageMagick's `import`: the game runs on its
own virtual display, with a Wine prefix under `--work`. On Windows it runs the
game natively (see "On Windows" below). Either way nothing is written to the
install.

```sh
# Record the original, run arklay on the same input, compare
scripts/oracle-re2.py scenario --input oracle/inputs-re2/street_walk.txt \
    --ticks 500 --out target/oracle-re2/street --pack re2.akpak

# Only record
scripts/oracle-re2.py record --ticks 500 --trace ref.trace

# Check that nothing but ticks decides what happens
scripts/oracle-re2.py determinism --ticks 1000 --out target/oracle-re2/det

# List the code Classic Rebirth changes
scripts/oracle-re2.py patches
```

`scenario` exits non-zero at any difference, as `oracle.py compare` does.

## How it works

The tool adopts the game's process and stops it with a breakpoint in `Pad_set`,
just after the call that reads the pad (`0x004D0F58`). Every tick passes there
once, and it's the only code the tool touches. At each stop it reads a line of
state from memory and puts the scripted pad value in `EAX`, so input goes through
the game's own mapping, edge detection and key repeat.

Ticks are counted, not timed. `determinism` records the same input twice, the
second time with a delay on every tick, and needs the two traces to be identical.

## On Windows

On Windows (`sys.platform == "win32"`) the same commands run the game natively, with no Wine, through the Win32 debug API (`scripts/oracle_re2_windows.py`, ctypes only, with Pillow for the pictures as on Linux). The game starts under `CreateProcessW` with `DEBUG_ONLY_THIS_PROCESS` from a tree of its own under `--work`: the executable and `ddraw.dll` copied, `data` a junction to the install's (a symbolic link needs a privilege on Windows), and `config.ini` with the same fixed settings as on Linux. The breakpoints (`BREAK_PAD` and `SsPlay`'s `BREAK_SOUND`) are `int3`s written with `WriteProcessMemory` and `FlushInstructionCache`, and are stepped over with the trap flag; `BREAK_PAD_BYTES` is checked as on Linux. The game is 32-bit and Python 64-bit, so the registers go through `Wow64GetThreadContext` and `Wow64SetThreadContext`, and the stops arrive as the WOW64 exception codes. As under ptrace, only the thread at `Pad_set` stops there: the tool takes its registers, suspends it and continues the debug event, so the game's other threads run while a stop's work is done. That matters with `--sound` (below). The game ends with the script, however it ends (`DebugSetProcessKillOnExit`), and the machine is kept from sleeping while it runs. The game's window opens on the desktop, without the focus.

Pictures come from Windows.Graphics.Capture, which hands over the window's own surface as DWM composes it: another window, or the system's (an update prompt, say), over the game doesn't change them, and the game's thread isn't asked for anything (`PrintWindow` waits for the window's thread, which is stopped at the breakpoint, and a copy of the screen shows whatever is on top). At a shot the tool waits for two compositions (`DwmFlush`) and takes the newest frame, cropped to the client area and placed at `FRAME_ORIGIN` on a 1024x768 image, so the files are the Linux path's. The game isn't DPI-aware, so it is started with the `HighDpiAware` compatibility layer, which keeps its client area at 640x480 on a scaled display, and the window's rounded corners (Windows 11) are turned off, since they would clip the picture's bottom corners. A minimised window has no picture, and DWM composes nothing while the display is off or the session is locked, so the display is kept on while pictures are taken, and a frame of play from a minimised window stops the record with a message, as do 300 pictures in a row with no new frame. Boot frames are skipped until the window is up.

`--sound` captures the game's own audio, and nothing else's, with process loopback (`VAD\Process_Loopback`, Windows 10 2004 and later), the counterpart of the PulseAudio sink: a 16-bit stereo 44.1 kHz `.wav`, each packet placed by its timestamp with silence in the gaps, so that the `.ticks` log's times line up with it as they do on Linux. The sound also plays on the speakers. The `.music` log and the `snd`, `bgm` and `xavol` fields are the same as on Linux.

With `DirectSoundEnable` on, a voice line ends by DirectSound's clock, not by ticks: `fg_status`'s `0x20` (and `0x20` in `0x130`) clears when it has played, so how many ticks a line holds depends on how much wall-clock time a tick takes, and Kendo's scene waits for its lines. On Linux and Windows alike, a `--sound` recording with pictures runs far slower than the game's 30 ticks a second (0.28 seconds a tick in the stored route, about 0.2 natively). A record that froze the whole game for a picture would hold the lines for more ticks still, which is why only the thread at `Pad_set` stops. So a `--sound` recording with a voice line in it is only reproduced on the ticks of another at that other's pace: `--pace TICKS_LOG` (on both systems) holds the thread at `Pad_set`, with the others running, until each traced tick is as far from tick 0 as it was in the recording whose `.ticks` log it is. Even then the bit can clear a tick or so apart, and two recordings at the same pace can differ there too: `determinism` with `--sound` over 1500 ticks of `door_101_102.txt` has `fgstat` differ on two ticks (1326 and 1449) and nothing else. Without `--sound` it is identical. The regression runner doesn't compare `fgstat`.

The game's fades are drawn off its own thread, on a clock (Classic Rebirth's, it seems): with the game stopped at `Pad_set`, the picture of a fade goes on changing for some 300 ms. So the frame of a tick in a fade depends on when it is taken, here two compositions after the stop and on Linux whenever `import` gets to it, and can be a step apart.

Recorded natively, the traces of the regression runner's references are byte for byte the Wine recordings of `item_take` (with `--sound` and every frame), `door_101_102` and `stairs_118_a`. `route_100_200` (with `--sound` and every frame, and `--pace` from its own `.ticks`) matches the Wine recording on every field of all 7400 ticks but `fgstat` on 14, at the ends of Kendo's lines (between 1310 and 2119) and one at 3457 to 3460, each a tick or three apart; without `--pace` its lines end later and the scene, and so the player, part from the Wine recording at tick 1331. `determinism` over 1500 ticks of `door_101_102.txt` without `--sound` is identical, and also identical to the first 1500 ticks of the Wine recording. The frames differ from Wine's by a mean of 0.012 to 0.016 per channel (out of 255, at 640x480) over `item_take`'s 1000 ticks of play and 0.031 over the route's 7400. The 2D frames of the status screen don't differ at all: what differs is the 3D, where native Direct3D and Wine's rasterise and filter edges and textures a little differently (a door's model during a load is the most, up to about 1.2, and the hall of room 200 up to 4.4), with the same poses in the same places, and the fades. Two frames of the route differ by more: tick 2, the original's first frame of the fade-in, shows natively, as in arklay, where Wine's is still black (29.7), and tick 3053, the first black one of room 102's door, is still the room natively (38.4); the route's other seven doors go black on the same tick on both.

## Ticks and input

Tick 0 is the first tick after the room's load has settled: a few ticks after
the player comes alive (`pl.life != 0`), which is when `Pl_init` has run and the
start position's collision push has landed. `--start leon` or `--start claire`
takes a fixed route there through the title screen: Original Mode, the
character, Normal, then confirm every 60 ticks until play begins. That takes 907
ticks for both, and they aren't traced. A line holds the state at the end of its
tick, and a pad value given for tick `t` first shows in line `t + 1`.

`--no-enemies` clears bit 0 of every enemy's `be_flg` at each stop, so nothing
runs them or collides with them. That leaves the player alone to compare with
arklay, which is how the routes are checked; the zombie recordings run with them
left on. `oracle/inputs-re2/` holds the scripts in use, and `street_wander.txt`
is a random walk through room 100.

## The regression runner

The original is deterministic, so a recording of it is made once and kept. `scripts/re2-regress.py` plays the runs in `oracle/re2-regress.toml` in arklay and compares each with its stored recording, with no Wine and no new recording. Run it for any change to RE 2's play, and read the lines it prints:

```sh
cargo build --profile test-release
scripts/re2-regress.py --out target/re2-regress              # every run, 3 at a time
scripts/re2-regress.py --out target/re2-regress item_take inv_mix   # named runs
scripts/re2-regress.py --out DIR --list                             # the runs and whether their references exist
```

`--out` is required and must not be under `/tmp`, a small RAM disk on the machines this runs on. The binary is `target/test-release/arklay` unless `--arklay` says otherwise. The pack is `--pack`, or else converted once into the output dir from `--game` or `ARKLAY_RE2_ROOT` (about 25 seconds). The references are in `--refs`, else `ARKLAY_RE2_REFS`, else `~/.local/share/arklay/re2-refs`: one folder per recording, with `ref.trace` and, where the run compares pictures, `frames/` (PNG, boot frames first), and a `meta.txt` with the input's checksum, the record command and the date. `--jobs` sets the parallelism (3 by default). arklay's frames and traces are deleted after the comparison unless `--keep` is given.

Each run prints one line: the trace verdict (`MATCH` and the number of ticks compared, or the number of matching ticks and the reference tick and fields of the first difference), the frames' mean error and three worst ticks when the run has frames (and the mean with the message box blanked, where the run has one), and `[ok]` or `[UNEXPECTED: ...]`. The last line is a summary, and the exit status is non-zero when any run is unexpected, a reference is missing (unless `--skip-missing`) or arklay fails. A run is `ok` when its trace matches the manifest's `expect`: `"match"`, or a known first divergence `{ tick, fields, note }` with the tick in the reference's numbering. `ignore = [[tick, "field"], ...]` leaves out differences that are known and one tick long, such as `rng` on a door's tick (see the doors above), so that what comes after them still counts. `frame_max_mean` fails a run whose mean frame error grows beyond it. A divergence that comes from a change is a regression: look at it with `oracle.py compare` and the `--keep`ed trace. One that is fixed makes its run `UNEXPECTED` until its `expect` is updated, which is the point: the manifest then says what is known.

A run starts arklay at the original's tick 344 (`offset`), so its input is the original's moved earlier (`input_shift`, or an `_arklay` file) and its setup script, a `.lua` in `oracle/inputs-re2/` or a `setup` table of the position, angle, health, `Rnd`, camera cut and flags that the runner writes out, puts the player where the original has them. Each `3:` entry is dropped from `snd` in both traces first, as in "Weapons", unless the run sets `keep_sound_3`. The runs cover the pick-ups, the inventory, the status screen and the weapons, the doors, route walks, runs and stairs from room 100 to room 200, the zombies' stands in rooms 610 and 11B, Kendo's scene, the crouching pick-up, the whole route in one run and the title. A run with `ui = "title"` plays arklay's `--ui title` against a `--boot` record ("The title"), with no setup script. Marvin's scene in room 202 and room 200's entry scene have references but no run yet: the first starts a tick apart from the original (see above) and the second has no recorded arklay start.

`scripts/re2-regress.py record NAME...` records a run's missing reference with `oracle-re2.py record` (it needs `--game` or `ARKLAY_RE2_ROOT`, and on Linux Wine and a display; it uses the Wine prefix, or on Windows the game's tree, under `--work`, or `wine` in `--out`), using the run's `record` arguments from the manifest and `--shot-dir` when the run has frames. It writes `ref.trace`, the sound's files and `frames/` into the refs dir and `meta.txt` beside them, and refuses to replace a reference unless `--force` is given. A `--sound` run with a voice line in it (Kendo's scene) is reproduced on another machine, or on the other system, only at the stored recording's pace: run `oracle-re2.py record` with `--pace` and the reference's `.ticks` (see "On Windows"). `--dry-run` prints the command. To add a run, add it to the manifest with its `record` arguments, record it, and run it: put the result you see, if it is a match or one of the divergences this file or `docs/re2-deviations.md` explains, in `expect`.
